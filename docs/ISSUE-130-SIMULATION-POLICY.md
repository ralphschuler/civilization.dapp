# Issue #130: versioned progression simulation and policy proposal

Status: proposal only. This document and its simulator do not alter an active contract, transaction path, deployment, or production configuration.

## Scope and deterministic rules

`src/simulation/policy-130-simulator.js` is a pure, versioned reference model. The current proposal identifier is `130.2`; a queued job must retain the identifier with which it was created. It accepts only integer inputs and levels 1–30. It covers these building classes:

| Class      | L1 base duration | Example role        |
| ---------- | ---------------: | ------------------- |
| production |            8 min | resource generation |
| logistics  |           10 min | storage / transport |
| military   |           12 min | barracks / defence  |
| civic      |           15 min | town / governance   |

Two candidate curves are compared: `steady` multiplies each next level by 1.1800, and `accelerated` by 1.1350. Each multiplication rounds **up** to whole seconds. This is deterministic across offline and online clients; it is not a claim about existing on-chain duration formulas.

The simulation permits one to three workshop construction slots: level 0 has none; levels 1–10 have 1, 11–20 have 2, and 21–30 have 3. Slot capacity permits parallel jobs, but the D1/D7/D30 table deliberately uses a single sequential slot so it is a conservative, comparable hypothesis.

## Hypotheses: one sequential civic queue, no resource or unlock blocking

| Horizon | Steady completed level | Accelerated completed level | Interpretation                                                    |
| ------- | ---------------------: | --------------------------: | ----------------------------------------------------------------- |
| D1      |                     11 |                          14 | Early onboarding should feel materially faster under accelerated. |
| D7      |                     20 |                          27 | Midgame pacing needs economy and retention review.                |
| D30     |                     30 |                          30 | Both curves reach the level cap; excess time has no level value.  |

These numbers are generated by `compareCurves({ buildingClass: "civic" })` with version `130.2`; they are hypotheses, not telemetry results. The model intentionally excludes live balances, prerequisite chains, raids, premium spending, and any chain timestamp.

## Reductions, caps, and sessions

The proposed named reductions are `rested` (10%), `cooperative` (15%), and one-time `migration` (20%). Names are deduplicated, added, and capped at 35%; the reduction calculation rounds upward, has a 60-second minimum duration, and has a 72-hour maximum duration per job. Tests cover rounding, duplicate boosts, the combination cap, and the minimum.

Passive/offline elapsed time is clamped to 72 hours (259,200 seconds), with negative elapsed time treated as zero. A session is only a client observation window: it neither extends this cap nor grants progress, and reconnecting cannot replay discarded elapsed time. Server/chain authority, if one is later chosen, must use a single captured timestamp and the stored job version; client clocks are display-only.

## Paid-advantage monthly cap (issues #130 and #208)

`evaluateMonthlyPaidAdvantage({ priorMonthlyWldEquivalent, requestedWldEquivalent })` is the source-only admission policy for the user-approved maximum of **5 WLD-equivalent per wallet per calendar month**. Both values are non-negative/positive `bigint` WLD-wei equivalents (`10^18` units per WLD); the result includes the fixed cap, prior usage, remaining allowance, admitted amount, rejected amount, `allowed`, and an explicit cap rejection reason. It is all-or-nothing: a request that exceeds the remaining allowance admits zero. The caller supplies the calendar-month bucket and its already aggregated usage; the module has no wallet identifier, clock, RPC, transaction, or hidden state.

`evaluateDirectConstructionBoost({ priorMonthlyWldEquivalent, requestedHours })` is an adapter for the current contract's exact direct price of 1 WLD per requested full hour. Consequently, with no prior paid use, five hours are admitted and six are rejected. A future CGOLD purchase must call the generic function with its explicitly established WLD-equivalent amount. The policy deliberately accepts no CGOLD token quantity or exchange-rate input, so it cannot invent an arbitrary CGOLD/WLD rate.

### Conservative CGOLD sale-rate calibration

Before any CGOLD sale route is proposed, governance should publish a modelled, time-bounded budget: forecast CGOLD gameplay issuance from Goldmine claims, raid-loot minting, and any configured reward-distributor campaign; then subtract modelled CGOLD sinks from building and troop burns plus planned buyback burns. Set any sale allocation/rate no higher than the conservative net amount supported by that model over the same period, with a safety margin and a hard issuance limit. Market inventory trades are not issuance (they exchange against an existing CGOLD reserve), so they must not be treated as a mint budget. Recalibrate only from published source/sink observations and keep the WLD-equivalent valuation used by the monthly cap explicit and auditable. This is a design rule, not an enabled sale or a chosen exchange rate.

## Fair migration and safety controls

Migration must be opt-in or automatically non-worsening per queued job. Existing jobs complete on their original version, with their original start/completion timestamp and slot occupancy. New jobs may select the approved newer version only after a published effective time. If migration would increase a job's completion time, preserve the earlier completion time; grant the migration reduction at most once per account and record it in an auditable migration ledger. No retroactive resource debit, forced cancellation, or reset is permitted.

Instrument only aggregated, privacy-minimised telemetry: policy version, class, level band (1–10 / 11–20 / 21–30), selected curve, boost set hash/count, slot saturation, job duration, offline-clamp count, completion/cancel outcome, and migration outcome. Do not store wallet signatures, session tokens, or raw IP addresses for this policy analysis.

For the first 14 days after any approved rollout, compare each policy-version cohort against the control daily: D1/D7/D30 completion, slot saturation, cancellation, 72-hour clamp rate, and error/revert rate. A 15% adverse relative movement in a pre-registered primary guardrail (D1 completion, cancellation, or error/revert rate) pauses new migration and new-version enrollment. Investigate, publish the decision, and retain existing jobs on their stored version.

## External review gate

No implementation may activate this proposal until an independent product/economy reviewer and a security reviewer both approve: parameters and level bands; fairness/migration copy and ledger; telemetry privacy review and 15% baseline definition; offline/session authority; and compatibility with active contracts. Approval must be recorded with the exact simulator version, test artifact, reviewer identities/roles, date, and rollback owner. This gate is intentionally external to the simulator and cannot be satisfied by a unit-test pass.
